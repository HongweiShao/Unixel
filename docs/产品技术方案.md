## 1. 技术栈
- **桌面框架**：Tauri 2（Rust 后端 + WebView 前端），相比 Electron 体积更小、内存更低、原生能力更强。
- **前端**：Vue 3 + TypeScript + Vite。
- **后端（Rust）**：
  - `dicom-rs` 0.7（`dicom-object`/`dicom-pixeldata`/`dicom-dictionary-std`/`dicom-core`）解码。
  - `image` 0.25（含 `png`/`jpeg`/`tiff` feature）常规图像解码与 PNG/JPEG 编码。
  - `nifti` 0.11（`features = ["ndarray_volumes"]`）NIfTI 体数据读写。
  - `openjph-core` 0.1 —— **纯 Rust** HTJ2K（JPEG 2000 Part 15）编解码，**无 C/C++ FFI、无 bindgen**。
  - `tauri-plugin-dialog` 文件对话框；`serde`/`serde_bytes` 序列化。
- **IPC**：Tauri command（`invoke`/`#[tauri::command]`），二进制走 `serde_bytes`。

## 4. 核心模块设计

### 4.1 解码管线（`decode_dicom_file` / `load_dicom`）
1. `dicom_object::open_file(path)` 打开 DICOM。
2. `obj.decode_pixel_data()` 取得 `DecodedPixelData`。
3. 读取 `columns/rows/number_of_frames/samples_per_pixel/bits_stored`；非单通道直接报错。
4. `pd.to_vec::<f32>()` —— **默认应用 Modality LUT**（Rescale）得到 HU 浮点帧。
5. 解析 `RescaleSlope/Intercept/WindowCenter/WindowWidth/PhotometricInterpretation`；DS 多值取首个。
6. 计算 HU 实际 `min/max`（非有限则回退 −1024/3071）。
7. f32 序列化为 LE 字节（`serde_bytes`）回传前端。

### 4.2 多格式解码（里程碑 B）
- **`decode_regular_image`**（`load_image`）：`image::open` → `to_luma8` → 灰度 u8 → f32；`DicomMeta` 缺省 slope=1/intercept=0、WC=128/WW=255、photometric=MONOCHROME2。
- **`decode_nifti`**（`load_nifti`）：`ReaderOptions::new().read_file` → `into_volume().into_ndarray::<f32>()`；校验 3D；**显式三重循环** `raw.push(volume[[x,y,z]])` 生成确定的 `[x][y][z]`（z 最内）布局，避免依赖 `into_raw_vec` 的内存排布假设（NIfTI 文件实际为 x 最内）。返回 `NiftiVolume { meta:NiftiMeta, voxel_bytes }`。
- **`decode_htj2k`**（`load_htj2k`）：读 `.j2c`/`.jph` 字节 → `htj2k_decode` → 灰度 u8 → f32 → 单帧 `DicomImage`。

### 4.3 窗映射（`windowing.ts` + Rust 镜像）
```
low    = WC − WW/2
scale  = 255 / WW   (WW>0)
v8 = clamp(round((HU[i] − low) × scale), 0, 255)
if MONOCHROME1: v8 = 255 − v8
RGBA = (v8, v8, v8, 255)
```
前端用于实时渲染；后端 `apply_window_rust` 实现同一公式，保证导出图像与屏幕一致。

### 4.4 导出管线（`export_frame_from_pixels` / `export_frame`）
1. 前端把**当前帧的 HU 浮点字节**（`pixel_bytes`）+ 尺寸/光度解释/窗设置经 `invoke("export_frame", {...})` 传入。
   - 设计决策：改为「前端传帧字节」而非「后端按 path 重新解码」，从而统一 DICOM/常规/NIfTI(MPR 切片)/HTJ2K 的导出入口——前端始终持有当前显示帧。
2. `apply_window_rust` → RGBA 缓冲。
3. 按 `format` 分派：
   - **HTJ2K**：RGBA 抽取灰度（`rgba.iter().step_by(4)`）→ `htj2k_encode(&gray, w, h, true)`（无损）→ 直接写字节。
   - **PNG**：`ImageBuffer::<Rgba<u8>>::from_raw` + `save`（无损）。
   - **JPEG**：RGBA→RGB（丢弃 Alpha），`JpegEncoder::new_with_quality(file, 1..100)` 编码。

### 4.5 HTJ2K 编解码（里程碑 C，`openjph-core`）
- **`htj2k_encode(gray, w, h, lossless)`**：
  - `Codestream::new()` → `access_siz_mut()` 设 image extent / 单组件 / `set_comp_info(0, (1,1), 8, false)` / tile size = 整图。
  - `access_cod_mut()`：`set_num_decomposition(5)`、`set_reversible(lossless)`（true=无损 TS 201）、`set_color_transform(false)`；`set_planar(0)`。
  - `MemOutfile` + `write_headers` → 逐行 `exchange(&line_i32, 0)` → `flush` → `get_data()`。
- **`htj2k_decode(codestream)`**：`MemInfile` + `read_headers` → `access_siz().get_width/get_height` → `create` → 逐行 `pull(0).ok_or(...)`（返回 `Option`，非 `Result`）→ 灰度 u8。

### 4.6 批量导出（`batch_export` / `try_export_one`，里程碑 C）
- 前端多选文件 + 选输出目录 → `invoke("batch_export", { paths, format, quality, outDir })`。
- 后端 `create_dir_all(out_dir)` 后逐文件 `try_export_one`：按扩展名路由到 `decode_any_to_frame`（NIfTI 取中间轴向切片 z=nz/2），再 `export_frame_from_pixels`；文件名内嵌 `{stem}_{format}_wc{wc}_ww{ww}.{ext}`。
- 汇总 `BatchResult { ok, failed: Vec<BatchFail> }`，前端横幅展示成功/失败计数与失败明细。

### 4.7 MPR 前端重建（`App.vue`）
- `extractNifti(axis, meta, volume)`：对 `[x][y][z]` 体数据按轴重排为帧序列（轴向宽 nx 高 ny、冠状宽 nx 高 nz、矢状宽 ny 高 nz），与后端 `decode_nifti` 布局严格一致。
- `niftiRender` 计算属性用 NIfTI 元数据构造 `DicomMeta`；`niftiKey` 在切换 MPR 视图时强制 `Viewer` 重挂载以重置帧索引。
- MPR 视图切换栏（轴向/冠状/矢状）+ 体尺寸显示。

### 4.8 前端查看器（`Viewer.vue`）
- 复用 `Uint8ClampedArray` RGBA 缓冲，离屏 canvas 按原分辨率绘制后再缩放上屏（`imageSmoothingEnabled=false` 保持像素清晰）。
- 交互：滚轮缩放、拖拽平移、`watch([wc,ww,frameIndex,zoom,pan], render)` 响应式重绘。
- 导出栏：格式选择（PNG/JPEG/HTJ2K）+ JPEG 质量滑块；`save()` 选路径后 `invoke("export_frame", { pixelBytes, ... })`。

## 5. 数据模型与接口契约

### 5.1 `DicomMeta`（前后端共享）
```ts
interface DicomMeta {
  path: string; filename: string;
  width: number; height: number; frames: number;
  bitsStored: number; pixelRepresentation: number; // 0=unsigned,1=signed
  slope: number; intercept: number;
  windowCenter: number; windowWidth: number;
  photometric: string;  // MONOCHROME1/2
  huMin: number; huMax: number;
}
```
### 5.2 `DicomImage`（`load_dicom`/`load_image`/`load_htj2k` 返回值）
```ts
interface DicomImage { meta: DicomMeta; pixelBytes: Uint8Array | string; }
// pixelBytes: f32 LE，顺序 [frame][row][col]，长度 = width*height*frames
```
### 5.3 `NiftiMeta` / `NiftiVolume`（`load_nifti` 返回值）
```ts
interface NiftiMeta { path: string; filename: string; dims:[number,number,number]; huMin:number; huMax:number; }
interface NiftiVolume { meta: NiftiMeta; voxelBytes: Uint8Array | string; }
// voxelBytes: f32 LE，顺序 [x][y][z]（z 最内），长度 = nx*ny*nz
```
### 5.4 `BatchResult` / `BatchFail`（`batch_export` 返回值）
```ts
interface BatchFail { path: string; error: string; }
interface BatchResult { ok: number; failed: BatchFail[]; }
```
### 5.5 Tauri Commands
| Command | 入参 | 返回 |
|---------|------|------|
| `load_dicom` | `{ path: string }` | `DicomImage` |
| `load_image` | `{ path: string }` | `DicomImage` |
| `load_nifti` | `{ path: string }` | `NiftiVolume` |
| `load_htj2k` | `{ path: string }` | `DicomImage` |
| `export_frame` | `{ pixelBytes:Vec<u8>, width:u32, height:u32, photometric:String, wc:f64, ww:f64, format:String, quality:u8, outputPath:String }` | `string`（输出路径） |
| `batch_export` | `{ paths:Vec<String>, format:String, quality:u8, outDir:String }` | `BatchResult` |

## 6. 关键技术决策与权衡
- **窗映射放前端**：保证交互实时性；导出时在 Rust 镜像同一公式，单一数学来源、避免偏差。
- **export_frame 改收「前端帧字节」**：统一 DICOM/常规/NIfTI(MPR)/HTJ2K 导出入口，前端始终持有当前显示帧；比「后端按 path 重解码」更通用（尤其 MPR 切片并非磁盘文件）。
- **HTJ2K 选用纯 Rust `openjph-core` 而非 OpenJPH C FFI**：`openjph-core` 是 OpenJPH 的 Rust 忠实移植，**无 C/C++ 依赖、无 bindgen、无跨平台原生构建风险**，集成与维护成本显著更低；API 覆盖编码/解码、可逆(5/3)/不可逆(9/7)小波、无损(TS 201)/有损(TS 203)。
- **NIfTI 显式 `[x][y][z]` 布局**：用逻辑索引三重循环而非 `into_raw_vec`，消除对 ndarray 内部内存排布假设的耦合，前后端布局严格一致、可测试。
- **JPEG 丢弃 Alpha**：JPEG 标准无 Alpha 通道，避免静默写入失败。
- **批量导出按文件默认窗**：实现简单、可直接单测；序列级分组/窗位预设为后续演进。
- **测试样本用纯标准库生成**：遵循 Python 隔离规则（managed venv + `array`/`math`），不引入 numpy 等重依赖。
- **对话框权限**：`capabilities/default.json` 开启 `dialog:default`（覆盖 open/save/目录选择）。

## 7. 测试策略
- **后端单元/集成测试**（`cargo test`）：
  - `decode_sample_ct`：校验尺寸/帧数/位深/有符号/Rescale 映射/HU 范围（空气≈−1024 HU）。
  - `export_sample_png_and_jpeg`：导出后读回校验 512×512 尺寸（PNG/JPEG）。
  - `htj2k_roundtrip_lossless`：48×32 灰度无损 HTJ2K 编码→解码像素完全一致。
  - `nifti_roundtrip`：32×24×16 体写入 `.nii.gz` 再读回，校验 `[x][y][z]` 布局（体素 (1,2,3) 期望值 6）。
- **前端类型与构建**：`vue-tsc --noEmit`、`vite build` 必须零错误（已验证 `vue-tsc` 通过、`vite build` 产物正常）。
- **手动冒烟**：`npm run tauri dev` 打开 `tests/sample.dcm` 调窗并导出；打开 NIfTI 验证 MPR；打开 `.j2c` 验证 HTJ2K 回显；批量导出核对文件名与计数。

## 8. 后续演进方案
- **压缩 DICOM 传输语法**：接入 GDCM/OpenJPH 以支持 JPEG2000/Lossy 等压缩语法解码。
- **序列分组管理面板（FR-06 后续）**：按 `SeriesInstanceUID` 分组、序列级窗位预设与批量操作 UI。
- **导出下放到 Rust/WASM 或 GPU**：超大分辨率（4K×4K 多帧）窗映射前移，缓解前端 CPU 压力。
- **HTJ2K 有损导出**：复用已有 `htj2k_encode(..., lossless=false)` 路径，导出器增加质量/码率参数（TS .203）。
- **DICOM SR 写回**：结构化报告生成与写回（当前为范围外）。

## 9. 构建与运行
```bash
npm install                 # 安装前端依赖（含 @tauri-apps/plugin-dialog）
npm run tauri dev           # 开发模式启动桌面应用
npm run tauri build         # 打包发布
cargo test                  # 后端测试（依赖首次编译较慢，约数分钟）
npm run build               # 前端类型检查 + 打包
```
> 注：Windows 环境下若 `cargo` 因 Defender 实时扫描锁定 `target/debug/.cargo-lock` 报「拒绝访问 (os error 5)」，可将项目目录加入 Windows Defender 排除项后重试；或使用独立 `CARGO_TARGET_DIR` 一次性构建。
