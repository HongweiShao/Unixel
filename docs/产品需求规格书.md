## 1. 产品概述

### 1.1 背景
专业影像技师与数据工程师在日常工作中需要对 DICOM 及常规影像进行**快速查看、窗位调校与格式转换导出**，但现有商业工具（如 OsiriX、RadiAnt）体积庞大、授权成本高，且难以嵌入自研数据处理流水线。医学影像处理软件（Unixel）定位为一款轻量、可本地离线运行、便于二次开发的桌面影像工具。

### 1.2 目标
- 提供离线、隐私安全的本地医学影像查看与处理能力。
- 覆盖 DICOM 与常规图像、体数据（NIfTI）的导入、查看、导出闭环。
- 提供 HTJ2K 高效压缩与批量转换能力，支撑大规模数据处理流水线。

### 1.3 目标用户
| 角色 | 核心诉求 |
|------|----------|
| 影像技师 | 快速调窗查看、导出指定窗位的 PNG/JPEG/HTJ2K 用于报告/会诊 |
| 数据工程师 | 将 DICOM/常规影像/NIfTI 体数据转换为标准格式，接入下游算法/训练流水线 |

### 1.4 范围
- **范围内**：桌面端（Windows/macOS/Linux）离线应用；本地文件导入；DICOM/常规图像/NIfTI 解码；窗宽窗位实时调校；PNG/JPEG/HTJ2K 导出；批量转换。
- **范围外（当前版本）**：PACS 联网拉取、云端存储、报告编辑、AI 诊断推理、DICOM 写入/结构化报告（SR）生成、按 SeriesInstanceUID 的序列分组管理面板。

## 2. 术语与定义
- **DICOM**：医学数字成像与通信标准，`.dcm`/`.dicom` 文件。
- **HU（Hounsfield Unit）**：CT 值单位；经 `像素值 × RescaleSlope + RescaleIntercept` 由原始值转换得到。
- **窗宽（WW）/窗位（WC）**：将 HU 动态范围线性映射到 8bit 灰度显示范围的参数。
- **MONOCHROME1/2**：光度解释；MONOCHROME1 表示值越大越暗（需反转显示）。
- **HTJ2K**：高性能 JPEG 2000（JPEG 2000 Part 15），支持无损（TS 1.2.840.10008.1.2.4.201）与有损压缩（TS .203）。
- **NIfTI**：神经影像体数据格式，`.nii`/`.nii.gz`。
- **MPR**：多平面重建（Multi-Planar Reconstruction）。

## 4. 详细功能需求

### FR-01 本地影像导入
- **FR-01.1** 通过系统文件对话框选择单个 `.dcm`/`.dicom` 文件。
- **FR-01.2** 后端用 `dicom-rs` 解码，自动应用 Modality LUT（Rescale Slope/Intercept），返回原始 HU 浮点帧。
- **FR-01.3** 解析并展示元数据：尺寸、帧数、位数、有/无符号、Slope/Intercept、默认窗宽窗位、光度解释、HU 范围。
- **FR-01.4** 仅支持单通道灰度影像；多样本彩色影像给出明确错误提示。
- **FR-01.5** 解码失败（如压缩传输语法未支持）返回可读中文错误。

### FR-02 影像查看
- **FR-02.1** 窗位（WC）、窗宽（WW）滑块实时调校，边界取 HU 实际范围。
- **FR-02.2** 鼠标滚轮缩放（0.1×–8×）、拖拽平移。
- **FR-02.3** 多帧影像可切换帧（滑块或按钮）。
- **FR-02.4** MONOCHROME1 自动反转显示。
- **FR-02.5** 重置按钮恢复默认窗位/缩放/平移/帧。
- **FR-02.6** 显示文件名、元数据条（尺寸/帧数/位深/光度解释/Slope/Intercept）。

### FR-03 窗位导出 PNG/JPEG
- **FR-03.1** 将「当前窗位/窗宽」下的当前帧导出为标准图像。
- **FR-03.2** 支持 PNG（无损）与 JPEG（可设质量 10–100）两种格式。
- **FR-03.3** 通过保存对话框指定输出路径，文件名建议含 WC/WW 标识。
- **FR-03.4** 导出成功/失败有明确状态反馈。
- **FR-03.5** 示例（mock）数据不可导出，按钮禁用并提示。

### FR-04 多格式导入（已实现）
- **FR-04.1 常规图像**：PNG/JPG/TIFF 经 `image` crate 解码为灰度帧，统一为 `DicomImage` 兼容结构（HU 缺省为原始 8bit 灰度，slope=1/intercept=0，默认 WC=128/WW=255）。
- **FR-04.2 NIfTI 体数据**：`nifti` 0.11 crate 读取 `.nii`/`.nii.gz`，解析为 3D 体（f32 LE，显式 `[x][y][z]`、z 最内布局）。
- **FR-04.3 MPR 三视图**：前端按轴把 3D 体重排为轴向/冠状/矢状帧序列，配 MPR 视图切换栏与体尺寸显示。
- **FR-04.4 统一入口**：`App.vue` 按扩展名路由到 `load_dicom`/`load_image`/`load_nifti`/`load_htj2k`。

### FR-05 HTJ2K 压缩/解压（已实现）
- **FR-05.1** 采用**纯 Rust `openjph-core` 0.1**（JPEG 2000 Part 15 的 Rust 忠实移植，**无 C/C++ FFI、无 bindgen**），规避原生编译与跨平台构建复杂性。
- **FR-05.2** 编码优先**无损**（可逆 5/3 小波，对应 TS 1.2.840.10008.1.2.4.201）；API 同时支持有损（TS .203）。
- **FR-05.3** 解码支持从 `.j2c`/`.jph` 回读为单帧灰度 `DicomImage`。
- **FR-05.4** 查看器导出栏新增 HTJ2K 选项，按当前窗位导出。

### FR-06 批量转换与导出（部分实现）
- **FR-06.1** 文件对话框多选文件 → 选择输出目录 → 批量解码并导出。
- **FR-06.2** 导出文件名内嵌格式、WC、WW 便于追溯；结果横幅显示成功/失败计数与失败明细。
- **FR-06.3 待后续**：按 `SeriesInstanceUID` 的序列分组、序列管理面板、序列级窗位预设（当前为「每文件按各自默认窗」的导出，NIfTI 取中间轴向切片）。

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 512×512 单帧解码 < 500ms；窗位调校实时（前端逐帧映射）；导出 < 1s |
| 兼容性 | Windows 10+/macOS 12+/主流 Linux；未压缩 DICOM 为主，压缩语法后续支持 |
| 安全 | 全程本地离线，无网络外传；不收集用户影像数据 |
| 可维护性 | 解码核心与 Tauri 解耦（可单元测试）；前后端契约明确（serde） |
| 可扩展性 | 解码器/导出器按格式注册，便于新增 NIfTI/HTJ2K |

## 6. 验收标准
- **AC-01**：打开示例 `.dcm` 可正确显示，空气区约为 −1024 HU、骨区约 +800 HU。
- **AC-02**：拖动 WC/WW 滑块画面实时变化，MONOCHROME1 样本正确反转。
- **AC-03**：导出 PNG/JPEG 可用图像软件打开，尺寸与原图一致，亮度与屏幕显示一致。
- **AC-04**：`cargo test` 全绿（含 `decode_sample_ct` / `export_sample_png_and_jpeg` / `htj2k_roundtrip_lossless` / `nifti_roundtrip`）；前端 `vue-tsc` 与 `vite build` 通过。
- **AC-05**：打开 NIfTI 体数据可切换轴向/冠状/矢状三视图；打开 `.j2c`/`.jph` 可正确回显；批量导出生成带 WC/WW 标识的文件。

## 7. 里程碑与路线图
- **里程碑 A（已完成）**：脚手架 → DICOM 解码 → 查看器 → 窗位导出 PNG/JPEG。
- **里程碑 B（已完成）**：多格式导入（常规图像 + NIfTI/MPR）。
- **里程碑 C（已完成）**：HTJ2K 压缩/解压（纯 Rust openjph-core）+ 批量转换与导出。
- **后续**：压缩 DICOM 传输语法接入、序列分组管理面板、超大分辨率下放到 Rust/WASM 或 GPU。

---

## 8. 已知限制与风险
- 当前仅支持未压缩 DICOM；JPEG2000/Lossy 等压缩传输语法需后续接入 GDCM/OpenJPH。
- 单帧窗映射在 CPU 端（前端 JS），超大分辨率（如 4K×4K 多帧）可能有性能压力，后续可下放到 Rust/WASM 或 GPU。
- 暂不支持 DICOM 结构化报告（SR）生成与写回。
- HTJ2K 导出目前为无损优先；有损（TS .203）编解码 API 已具备，可在导出器增加质量参数后启用。
- 批量导出为「每文件按默认窗」模式，尚未实现序列级分组与窗位预设管理。
